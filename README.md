# AI 旅行规划工作台

面向第九届“传智杯”AI WEB 网页开发挑战赛的旅行规划 Web 项目。重点是可编辑、可解释的完整行程，而不是让 AI 输出一篇攻略。

> 当前实现：单城市 1—14 日、1—20 人，完整需求→公共候选与 AI 提纲→相邻步行／三餐排程→可编辑提案的离线闭环。首页与工作台采用暖纸／松绿；地点搜索融入完整需求，生成显示实际阶段／处理天数与取消，重复有效景点显式去重。结果采用概览／日期→默认可见地图→每日重点与安排的垂直布局，桌面／手机均为单一主滚动，保留双锁、原生拖拽／跨天排序、营业预约、费用与确认撤销。后台已支持从审核后的同城社交资料索引自动匹配最多三篇供 AI 参考，不要求最终用户上传；实际采集端与真实资料源尚未配置。旧文件／图片导入只是辅助工具，不是自动采集或已核验平台图库。
>
> 验证边界：真实完整生成／14 日质量、窄屏新版 SDK、天气账号、平台图片与展示权、交通比较、实际行情／分日费用、权限保存分享仍未完成；所有供应商均未达 P。刷新清空方案与图片，页面保留不是持久化。最新离线验证为 499 单测／222 双端 E2E／生产构建通过，历次结果及失败见[测试记录](docs/testing.md)，真实证据及许可见[接口核验记录](docs/api-verification.md)，视觉约定见 [DESIGN.md](DESIGN.md)。

## 1. 产品目标与边界

用户已确认新版为浅色专业旅行工作台：单城市 1—14 日、1—20 人。输入目的地、日期与首末日／每日可用时段、人数、人均或全体预算及计入范围、必去地点、必吃菜品或餐厅、主要与次要旅行目的、节奏和饮食限制后，AI 直接给出完整方案；没有必去／必吃清单也应能生成，不要求用户先手工挑齐地点或录完三餐。

方案按日给出何时去何地、做什么／多久、三餐吃什么及餐厅建议、地点间交通方式／耗时、全程与每日费用分配，并支持地图联动、锁定、替换、差异确认及撤销。目的包括民风与当地生活、历史文化、自然、美食、休闲、摄影；必去／必吃与时间预算冲突须明确报告，不能为凑完整而静默删约束。营业、菜品供应、票价、余票、过敏安全与超预报期天气未经证据核实不得写成确定事实；预算分配建议不等于实时报价。

最终方案须图文并茂、优雅大气，呈现为可浏览的旅行提案册，而非纯文字攻略或长表格：目的地封面与旅行主题、每日主题及地点图文、吃玩时间轴、逐段交通与真实地图、每日／全程费用概览；编辑能力仍保留。使用有明确来源和展示权限、与具体地点相符的图片，不用无关照片冒充实景，不让模型指定任意图片 URL；没有可信素材时采用清晰的地图／排版呈现，不伪造实景或隐藏缺失。用户已取消美团／大众点评接入，改以 MediaCrawler 采集的已获权社交内容作为旅行灵感与推荐依据，地点与路线仍由高德核对；[GitHub 调查](docs/api-verification.md#10-github-旅行产品参考调查2026-10-28)已核对四个项目的代码／截图与许可证，仅作为实现参考。首轮已补 AI 体验说明、重点／游玩或点餐建议与行前核实、提案层次与日期切换动效，以及地图分类编号、路线描边／方向／相邻高亮和全日视野；旧快照无指南时不伪造内容，AI 建议不当已核实地点介绍。双端实际页面已回读，动效尊重 reduced motion，保留浅色工作台、编辑保护和窄屏重排；新地图绘制只做离线样式／分段验证，真实 SDK 效果尚未复验；地点已支持独立授权图片导入／公开链接与当前会话关联，真实平台文件与目的地摄影封面仍未验收。MediaCrawler 为非商业学习许可，独立采集端与网站分离；已接小红书文件导入／候选核对／模型参考与来源列表的离线闭环，尚未运行平台采集或真实文件联调。社交照片仍须核对展示授权，不因可抓取或代码可用而自动放行。预算图表只展示有依据的金额或明确标记的目标分配，未知不画成零元。

新版布局可替换原 Figma 静态稿：突出每日完整时间轴与真实地图，预算／天气／来源按需展开，保持克制配色、清晰字级和留白，保留可访问操作与窄屏重排。技术栈、默认模型及数据安全边界不变。首页已接新版完整需求→AI 提纲→真实相邻步行→三餐与活动排程→逐日提案页面，旧 2—3 日／最多六地点手动流程保留在工作台次级工具中，`/manual` 为兼容链接。新增流式取消、目标预算图及本地替换预览／确认／撤销；检查 66 的 304 单测／114 E2E／build 已通过，新增入口、逐日主题／三餐时间轴、地图无配置、全程目标图及每日均分参考完成双端离线闭环，并回读实际 viewport 与窄屏地图态；非真实完整生成或最终图文验收。检查 73 将手动日级天气按需展开接到新版 14 日／20 人方案，显式查询、来源／粒度、时间锁不变及第 14 日超范围真实无配置 HTTP 双端验证通过；无真实天气调用。公交比较、真实平台图片、天气替代、景点／餐厅替换及权限保存分享仍待验收；全规模停留、双锁与排序编辑已有离线证据，旧绿色结果不能代替完整产品完成。城市仍待用户确认，杭州仅为此前实测与 fixture 示例，不写死为正式目的地。

### 首版范围

- 首页／探索、新建计划、规划工作台、只读分享。
- 地点搜索、地图联动、步行及公交／地铁分段。
- 景点开放与预约提示；完整每日活动与三餐规划、餐厅主选及备选。
- 天气风险提醒、室内替代方案的预览与确认。
- 拖拽调整、锁定地点／时间、冲突提示、版本撤销。
- 分类预算：跨城交通、市内交通、住宿、餐饮和门票。
- 手动录入铁路／航班的出发、到达、返程时间及车站／机场，参与接驳和时间约束。
- 保存与可撤销的只读分享；无需先建设完整账号体系。

### 待验证扩展

- MediaCrawler 实际采集与资料索引同步、多平台正文支持；当前后台资料索引及辅助导入仅接受小红书白名单，尚无真实平台文件联调。
- 聚合数据铁路时刻、席别票价和余票查询。
- 航班时刻／动态查询；实时机票报价另行评估供应商。
- 基于授权评论的证据化摘要。

这些能力默认关闭，不作为首版运行依赖。未取得权限不显示“已接入”。

### 不做

出票、支付、退改签、酒店预订、社区、多城市自动规划、未经许可的平台评论抓取、实时景区客流监测。首版不引入微服务、多 Agent 或大型向量数据库。

## 2. 技术栈

采用单仓库、模块化单体，前后端统一 TypeScript。

| 层次 | 选型 | 职责 |
| --- | --- | --- |
| Web 与服务端 | Next.js App Router、React、TypeScript | 页面、同源 Route Handlers、服务端编排 |
| 样式与组件 | Tailwind CSS、shadcn/ui | 一致的交互与响应式界面 |
| 地图 | 高德 JS API 2.0 | 标记、真实路线与地点联动 |
| 拖拽与状态 | dnd-kit、Zustand、TanStack Query | 拖拽、未保存草稿、服务端数据请求 |
| 数据校验 | Zod | 表单、API、供应商响应与模型结构化输出 |
| AI | 服务端原生 OpenAI 兼容 HTTP；默认 DeepSeek | 受约束地点推荐／每日提纲；完整编排尚在离线验证，修改提案待接 |
| 持久化 | PostgreSQL、Drizzle | 行程、版本、分享权限、人工资料 |
| 测试 | Vitest、Playwright | 规划器、适配器、工作台交互 |

上述为架构选型，按阶段实施；已安装依赖与精确版本见 `package.json` 和锁文件。shadcn/ui、dnd-kit 尚未引入；数据库运行时／迁移依赖已获用户授权并安装，五表结构及未执行的 SQL 迁移已生成并静态检查，连接、权限与持久化应用模块尚未实现，不把选型写成已完成；AI 当前直接使用原生 fetch 接 OpenAI 兼容格式，没有安装模型 SDK。

## 3. 总体架构

```text
浏览器：表单 + 行程时间轴 + 地图 + 详情 + 预算／天气
  │ 同源 API；浏览器不携带供应商私密凭据
  ▼
Next.js Route Handlers
  │ 输入校验、所有权校验、限流、请求标识
  ▼
应用服务：生成计划 / 提出修改 / 预览 / 确认 / 分享
  ├─ AI：理解需求、解释事实、输出受约束的修改操作
  ├─ Planner：候选筛选、时间窗排程、餐饮插入、局部优化
  ├─ Validator：时间、开放、交通、预约、预算与锁定检查
  ├─ Providers：高德 / 天气 / 人工资料 / 可选铁路、餐饮、航班
  └─ Repositories：PostgreSQL + 版本与权限
```

依赖方向：`UI → HTTP → services → domain / providers / db`。领域算法不依赖 React、Next.js、模型 SDK 或供应商原始响应；供应商适配器不直接修改行程。

### 规划数据流

1. 表单或自然语言输入通过 Zod 校验；AI 解析结果回填表单，关键未知项由用户确认。
2. 人工资料和地点接口提供候选；读取可用天气及到达／返程约束。
3. 放入固定时间、必去地点、用餐和休息窗口，再做候选贪心插入。
4. 地理粗筛后只查询候选关键路段，按实际路线耗时重新排程。
5. 通过局部交换、跨天移动、替换改善偏好匹配、绕路、预算与天气风险。
6. 每次修改后校验；输出 `feasible / unverified / infeasible` 及原因，而非一律宣称可行。
7. AI 基于结果和来源解释推荐，不创造地点、开放时间、票价或天气。

高德公交方案总耗时已包含等车时间，归一化后不重复加算；另加的进站、接驳、休息缓冲要分别标明。门到门比较包括两端接驳和可调整的安检／出站缓冲，而不只比较列车或飞机运行时长。

### 餐饮规划

以午晚餐时间窗和前后地点筛选餐厅，检查营业、口味与预算；按“顺路、特色、预算友好”展示候选。

```text
额外绕路耗时 = 前一地点 → 餐厅 → 后一地点 − 前一地点 → 后一地点
```

真实路线耗时参与最终选择，直线距离只用于粗筛。无实时排队数据则显示未知；没有过敏相关可靠信息时不承诺安全，提示向商家确认。

### 修改、确认与撤销

```text
用户调整或 AI 请求
→ 生成 Proposal（携带 baseVersion）
→ 计算候选行程、校验、展示前后差异
→ 用户确认
→ 服务端复验与原子提交新版本
```

- AI 只输出允许的操作，例如移动、替换、删除、调整停留时间，不直接写数据库。
- 候选地点必须来自已有候选 ID；禁止提交模型自创 ID。
- `baseVersion` 不匹配返回版本冲突，重新预览，不覆盖其他修改。
- 确认时复验锁定、权限与所依赖数据的新鲜度；变化影响结果则要求重新预览。
- 地点锁与时间锁分开表达；用户手动排序后不偷偷恢复算法排序。
- 撤销恢复历史内容并生成新版本，不删除已有版本记录。

## 4. 数据与接口契约

### 领域模型

| 模型 | 核心内容 |
| --- | --- |
| TripInput | 城市、日期、人数、偏好、预算口径、起终点与饮食限制 |
| Place | 内部 ID、供应商 ID、坐标及坐标系、分类、入口、开放、预约、费用、室内外属性 |
| Evidence | 来源 URL／标识、来源日期、查询日期、许可备注、数据性质 |
| TransportLeg | 起终点、方式、出发时刻、耗时、费用、换乘、线路及来源 |
| IntercitySegment | 铁路／航班、完整出发到达日期时间、车站／机场、用户录入或接口来源 |
| WeatherSnapshot | 有效时段、日级／小时级粒度、更新时间、地点及来源 |
| ReviewInsight | 授权原文证据 ID、摘要、适用人群、时间；无证据不生成 |
| ItineraryItem | 景点／餐饮／休息／跨城节点、时间窗、停留时长、地点锁和时间锁 |
| PlanVersion / Proposal | 行程快照、前一版本、修改操作、基准版本、校验报告 |
| BudgetSummary | 各分类金额、每人／总额、估算区间、未知费用项 |
| GuestSession / ShareLink | 匿名编辑权限、分享快照、令牌摘要、到期与撤销状态 |

数据性质采用 `provider / curated / user / estimate / fixture`，并记录来源和有效时间；缺失值是 `null`，不是零。供应商数据也不等于绝对正确：每个关键字段的来源和时效可单独追踪。

- 金额使用整数分并记录币种；预算默认包含跨城往返、住宿、餐饮、门票与市内交通，不含购物，允许用户关闭跨城计入。
- 人均餐饮费用按人数计算；跨城票价按实际录入或查询席别计算；未知费用使总额成为不完整估算。
- 保存 ISO 日期时间与时区；首版国内行程使用 `Asia/Shanghai`，跨午夜班次必须保留到达日期。
- 高德路线／展示坐标使用 GCJ-02；其他坐标保留原始坐标系。天气坐标按供应商要求转换，不能默认为与地图一致。
- 开放和预约规则保留有效日期；“需预约”不等于“已预约”。
- 拥挤度仅做规则估计，显示“非实时监测”；不得把道路拥堵等同于景区客流。

### 供应商边界

按能力定义 `PlaceProvider`、`RouteProvider`、`WeatherProvider`、`RestaurantProvider`、`RailProvider`、`FlightProvider`，避免把全部能力塞进一个万能客户端。

适配器返回经校验的领域数据和状态：`ok / not_configured / permission_denied / unavailable / out_of_range`。异常、空结果、缺字段分别处理，HTTP 200 不代表业务成功。可选接口未开通时关闭对应入口；人工录入始终标明来源。

AI 工具仅封装可信服务：`searchPlaces`、`getPlaceFacts`、`getWeather`、`calculateRoute`、`proposePlanChanges`。评论和地点文本都是不可信内容，不可作为改变工具权限的指令。

### 计划中的 HTTP API

| 接口 | 用途 |
| --- | --- |
| `GET /api/places` | 有边界的地点／餐饮搜索 |
| `POST /api/weather` | 天气与粒度、有效范围；坐标放请求体避免 URL 日志 |
| `POST /api/routes` | 指定时刻的路段规划 |
| `POST /api/plans` | 旧手动页生成路线草稿，不持久化 |
| `POST /api/itineraries` | 新版 TripBrief→候选与 AI 提纲→相邻步行／三餐排程，NDJSON 进度及完整结果，不持久化 |
| `GET /api/plans/:id` | 读取有权限的行程 |
| `POST /api/plans/:id/proposals` | 生成修改预览，不覆盖已保存版本 |
| `POST /api/plans/:id/proposals/:proposalId/apply` | 复验并确认修改 |
| `POST /api/plans/:id/restore` | 将指定历史版本恢复为新版本 |
| `POST /api/plans/:id/shares` | 创建只读脱敏快照链接 |
| `DELETE /api/plans/:id/shares/:shareId` | 撤销分享 |
| `GET /api/shares/:token` | 读取有效的只读快照 |

当前实现 `GET /api/places`、`POST /api/routes`（步行）、`POST /api/plans`（只生成草稿）、`POST /api/recommendations`（AI 从真实候选推荐）、`POST /api/itineraries`（完整生成，仅离线验收）及 `POST /api/weather`（仅离线契约与界面验证，未真实调用）。其余接口尚未实现。铁路和航班 API 路由等实际验证通过再添加。

## 5. 页面与状态

- `/`：首页介绍与规划入口，`/explore` 为别名；旅行提案纸张构图为装饰示意，不当实景或真实生成方案。
- `/plan`：完整规划主入口；偏好区可搜索公共地点并补充必去名称，生成时重新核对，不自动启动 AI。旧手动选点保留在「手动草稿工具」，各自保留输入／选点／结果；生成结果在原页展示，切换不自动查询，生成中须先取消或等待。`/manual` 保留兼容链接。
- `/itinerary`：当前 AI 提案及差异预览，无方案时展示新建入口；不是手动草稿列表或服务端保存。软导航保留页面会话中的 AI 方案，刷新清空。
- 自动社交参考：点击生成后，由后台读取运营方审核的资料索引，按同城与旅行偏好去重、选最多三篇供当前模型参考，再核对其中的公共地点和路线。请求 brief 保持原样，返回的 socialSource 独立标记来源与状态；结果可查看规范引用。没有可用资料时明确未使用，不把模型记忆包装成平台检索。运行配置见接口核验第 16 节，最终用户无需上传；当前没有真实采集端或资料索引。

## 7. 安全、配额与降级

- 私密凭据只在服务端配置；地图 JS Key 属于公开客户端标识，使用独立 Key、域名限制及供应商推荐的安全代理配置。Web 服务 Key 不能放入 `NEXT_PUBLIC_*`。
- 所有供应商请求有超时、并发上限、有限重试和调用计数；401／403 不盲目重试。不对所有候选地点请求全量两点路线矩阵。
- 仅在许可允许时缓存／保存供应商数据；TTL 和可保存字段在账号验证后确定。历史快照也须遵守许可，不能借版本保存绕过存储限制。
- 没有路线时保留草稿并标明“交通未校验”，不把直线距离包装成真实路线。天气缺失显示未知，不自动编造雨天。
- 演示模式只能明确选择，使用独立 fixtures 并醒目标注；生产错误不静默切换到假数据。
- 匿名编辑使用高熵令牌、服务端摘要校验、HttpOnly／SameSite Cookie（生产启用 Secure）；写接口校验来源以防 CSRF。不可只凭行程 ID 或客户端 ownerId 授权。
- 分享使用独立可撤销令牌和脱敏快照，默认不包含姓名、联系方式、精确住宿地址、订单与票据；链接不赋予编辑权限。
- 限制外部请求目标为已配置供应商，不能让模型或用户指定任意 URL；日志脱敏，不记录完整凭据、票据或私密位置。

当前仅在本机运行，不作上线准备完成的承诺。草稿只保存在页面内存，刷新即丢失；仅保留当前草稿、一次撤销快照及当前弹窗的已查询路段，不做服务端供应商结果缓存，供应商原始响应不入库。API 有进程级调用预算与并发保护，但不是生产分布式限流。

用户已授权 PostgreSQL＋Drizzle 相关依赖并选择提供本地数据库：在被忽略的 `.env.local` 配置 `DATABASE_URL`，不要向聊天发送连接串；安装依赖不自动连接或迁移。`npm run db:generate` 只生成 SQL，无凭据、不连接；现有五表／外键／摘要约束已静态复核，并新增凭证／Cookie 参数、许可 TTL 门禁与严格脱敏分享 DTO 的离线辅助规则；不是会话授权、分享链接或数据库集成验收，不运行 push／migrate 或连接非专用数据库。天气已实现新版每日契约适配、同源 POST、日期范围判断与手动查询面板；须确认参考点在中国大陆，其他地区坐标系未支持，范围检查不等于国境判断。昼夜仍属日级预报，保留缺失／部分覆盖、查询时间／未知更新时间与归因；切日期或参考点中止请求并清空当前视图结果，不持久化或服务端缓存，不自动重试／改行程。服务端配置 `QWEATHER_API_HOST`，与 `QWEATHER_JWT`／`QWEATHER_API_KEY` 二选一；只支持预生成 JWT，不读取签名私钥。当前只完成离线 fixture、无配置及超范围 HTTP 验证，真实账号与展示／保存许可仍需确认及单独调用授权；日期／昼夜范围与参考点一致性已补回归通过，见检查 32—34。数据库／迁移精确版本见锁文件；检查 27 曾有 5 high（Next ESLint 间接依赖）与 4 moderate（Drizzle Kit 间接 esbuild 工具依赖）、生产审计 0；检查 68 的 Next 16.4.0 生产 critical 已经用户授权升级至 16.4.3，检查 69 生产审计恢复 0，完整依赖仍有 4 moderate（Drizzle Kit 工具链），不运行 Studio 或相关开发 HTTP server，不把告警写成已解决。
