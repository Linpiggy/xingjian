## 设计方向

- 面向大众旅行规划的工具型界面，以表单、时间轴、地图、地点详情和修改差异为中心，不使用聊天窗口代替产品。
- “行间”为暂用名称，不代表用户已确定品牌；杭州、日期、行程与金额均是设计示例。
- Noto Sans SC 中文字体，青绿色主色与中性浅色背景。警告、错误色仅用于语义状态。
- 桌面三栏布局，为行程、地图和详情联动预留选中状态；窄屏设计行程／地图切换控件。实际切换、详情抽屉、拖拽和键盘调整需在应用实现阶段补齐。
- 按钮／输入圆角 8、面板圆角 12、标签圆角 99；普通操作按钮高 48，图标操作区至少 44。
- 15 个颜色变量绑定在 `Travel Planner` 集合。当前文件创建第二模式时报 `Limited to 1 modes only`，所以实际只交付 Light 模式。`tokens.json` 中 Dark 值是后续候选，不宣称已在 Figma 验证。

## 数据和交互边界

高德接口已经完成代表性账号实测，详见 [接口核验记录](../../docs/api-verification.md)。但设计中地图为自绘示意图，不是高德底图，点位与连线不能用于实际导航。

天气按用户要求假设可接入，仅展示明确标注的示例，和风天气没有实测。餐饮营业时间、人均消费、门票与预约等未知信息不填成零、不伪造评分或网友评论。

所有页面是静态可编辑设计稿。原生 prototype reaction 写入在本次会话中未通过复查，因此不交付“已打通点击流程”的承诺；生成、保存、撤销、分享、地图切换和应用修改等按钮尚不执行真实操作。预览页将不完整方案保存为“待核实草稿”，不标记为可执行。

## 源文件与复核

- `build-screens.py`：生成四个页面的 JSX 设计结构，不是 React 应用代码。
- `screen-01.jsx` 至 `screen-04.jsx`、`screens.json`：FigCli 渲染输入。
- `states.json`：四个状态组件的渲染输入。
- `tokens.json`：本次颜色与候选明暗色值。
- `render.mjs`：调用已安装的 FigCli `render-batch`，不通过 eval 创建视觉节点。
- `finish.js`：本次文件特定节点的修整记录，ID 只适用于当前文件；不能对另一文件直接执行。
- `exports/manifest.json`：节点、真实尺寸和检查摘要。
- `exports/*.measure.json`、`exports/*.a11y.json`：测量与自动审计记录。

重建会新增图层，不会替换原稿；不要对已有文件无检查地重复运行。CLI 多行文本和浮层几何存在解析限制，最终 Figma 原生稿与经检查的 PNG 是视觉验收依据，源结构需结合节点测量复核。

8 个交付节点均已 `verify --measure`，逐张检查 PNG，自动 AA 审计均为 0 error / 0 warning。这个结果仅覆盖工具对设计图层的检查，不等于浏览器键盘、焦点、响应式行为或屏幕阅读器已经通过。

下一步是确认视觉方向，再建立 Next.js 脚手架，先实现表单与工作台静态布局，然后接入高德；天气仍需在正式接入时验证。
